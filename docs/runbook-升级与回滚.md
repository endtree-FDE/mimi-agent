# 升级与回滚：运维手册

这一页是**已经在真机上跑通过的那一套**，不是设想。它讲三件事：升级走哪几步、每一步的判据是什么（不过就停手）、以及怎么回滚。

对着机器操作的细节在别处，本页只串顺序和闸门：

- 每一项检查读什么、JSON 里哪个字段决定结论：见 [部署后验证.md](部署后验证.md)
- 停机、单实例锁、进程号被复用：见 [升级停机与单实例.md](升级停机与单实例.md)
- 多个机器人逐个升：见 [升级三个机器人.md](升级三个机器人.md)
- 动过模型或提示词之后的质量回归：见 [回归测试.md](回归测试.md)

## 前提

- 一次只动一个实例目录。另外几个保持运行，出问题时可以对照，也不会同时全断。
- 待升的那一版**先在源仓库跑绿测试**，再往实例目录上取。还在草稿里的改动不拿去替换正在服务的程序。
- 实例目录的 `agents\` 配置**不由升级改动**。配置要改是另一件事，改之前单独确认，并留一份能还原的副本。
- 下面的路径都是本机绝对路径的例子，照你自己的目录换。

## 四步口径

对外只说四步，内部展开成八条命令。顺序是有原因的，不要自己换。

| 对外 | 内部命令 | 为什么在这个位置 |
|---|---|---|
| 1 前置核对 | `python checks\verify_deploy.py --base D:\bots\甲 -c agents\甲.json --no-doctor` | 先确认「现在这台是好的」。带着已有故障去升级，事后分不清是哪一步弄坏的 |
| 2 取代码并验收 | `git -C D:\bots\甲 fetch <源> main` → `git -C D:\bots\甲 merge --ff-only FETCH_HEAD` → `set PYTHONUTF8=1 && python tests\run_tests.py` → `git -C D:\bots\甲 tag -a deploy/甲-20261104 FETCH_HEAD` | 只有前三步都过了才打标注 tag，标签才等于「这台跑的是这一版，且它测过」 |
| 3 平滑重启 | 先放锁（`scripts\botproc.ps1` 的 `Set-DeployLock`）→ `scripts\reload.ps1 -Config agents\甲.json` | 见下面「放锁为什么在合并之后」 |
| 4 复核并释放锁 | `python checks\verify_deploy.py --base D:\bots\甲 -c agents\甲.json` → `Clear-DeployLock` | 锁不释放，看门狗会一直让路，下一次真故障就没人拉 |

放锁和释放锁都在那个目录自己的 `scripts\botproc.ps1` 里，不要手改 `state\deploy.lock`。

### 放锁为什么在合并之后

2026-11-03 那次是这么踩的：旧版 `scripts\watchdog.ps1` 认不出 `state\deploy.lock`，放早了它照样每五分钟重启一次，锁形同虚设。合并之后新看门狗和 `Set-DeployLock` 才同时到位，这时候放锁才真挡住重启。

所以顺序是**取代码 → 测试 → 标注 → 放锁 → 重启 → 核对 → 释放锁**。

## 闸门：不过就停手，不要绕

每条都实测到过，写在下面的判据而不是「小心一点」。

**前置快进核对**（在做第 2 步之前用只读命令算出来，别等 `git` 报错）：

- `git -C <源> merge-base --is-ancestor <实例目录 HEAD> main` 返回 0，说明实例那个提交在源 `main` 的历史里，`--ff-only` 才会被接受。不为 0 表示那个目录有本地提交或来自别的线，**必须人工先决定**，脚本不该假装成功。
- 本地已跟踪的改动（`git diff --name-only`）和这次要带进来的文件撞名 → `git merge` 会拒绝。先挪开或提交。
- 本地未跟踪的文件和这次新增的文件同名 → 同样会被拒绝。线上目录常有本地攒出来的日志、kb、`.bak`，这一条最容易撞上。
- 实例目录当前分支不是 `main` → 先确认这个目录归谁、在跟哪条线，再谈升级。

**测试**：`python tests\run_tests.py` 一条红就停下。Windows 上带 `PYTHONUTF8=1` 和不带都跑一遍更稳——不带时按 cp936 读文件，写死 UTF-8 的测试夹具会在那儿挂，而 CI 的 windows 那一格恰好两种都跑。

CI 的 Lint 那一格还盯一件只在 Linux 上才暴露的事：测试里的 Windows 形状路径。`"C:/x"` 这种串在 Windows 上算绝对路径、在 Linux 上只是普通相对路径，`os.path.join(base, "C:/x")` 在前者直接丢掉 `base`、在后者把两段拼起来，所以同一行断言两个系统测的**不是同一件事**，而它看起来一直是绿的。要「一个绝对路径」就用 `tempfile.gettempdir()` 现取；确实要 Windows 形状（假进程表、假命令行、盘符拒绝用例）时写一行声明，说明为什么这串就该是那个形状。

**重启之后**（`checks\verify_deploy.py` 的 JSON，只读 `status` 和 `fails`）：

- `status` 必须是 `PASS`。`warns` 的条数不是固定的，带不带 `--doctor` 差好几条，别拿条数当闸门。
- `topology.serving` 必须是 1。0 或 2 都是 `FAIL`；0 有两种意思——进程真没起来，或者进程表没读到（后者只提示，不猜）。
- `runtime.restart_pending` 为真只写进 `warns`，不改结论。它专指「代码合完了、进程还是旧的」那段窗口，这一版到位之后必须为假。
- `heartbeat` 年龄超过 `alerts.unhealthy_after_sec`（没写按 180 秒）是 `FAIL`。别用日志里有没有新行当活着的判据，要看 `state\heartbeat` 的年龄。
- `git.tags` 为空只进 `warns`：意思是「说不清这台跑的是哪版」。这就是第 2 步要打标注 tag 的理由。
- `config.kb`：目录在不在、认哪些扩展名、能检索到几条。`exists` 为真但 `files` 为 0 只提醒；知识库检索和 `kb_index` 都关着时连提醒都没有，那是正常配置。

任何一步失败就**停在那里**，不要接着跑后面的命令。锁由执行者负责释放——忘了释放的后果是看门狗一直让路。

## 回滚

回滚比重启更危险：看门狗会把坏实例反复拉起来。顺序如下，每一步都要校验，任一步不过就停下。

1. 前置：要退回的那个提交在本地存在（`git cat-file -t <sha>`），配置副本在。
2. **先停用看门狗那条计划任务**，再动代码。失败时故意让它留在 Disabled——宁可没人拉，也不要反复拉起坏实例。
3. `scripts\stop.ps1` 停机器人，然后确认本目录的 `agentbot.py` 进程真的不在了。
4. `git -C D:\bots\甲 reset --hard <旧提交>`。
5. 核对工作区里**升级之前的既有意图**没被这次 `reset --hard` 吞掉（未跟踪的文件、你已经删掉的东西）。这一条最容易被跳过，因为第 4 步看起来总是成功的。
6. 配置仍是升级前那一份（比对 sha256，不要只看文件在不在）。
7. `scripts\start.ps1` 启动。
8. 心跳：`state\heartbeat` 年龄小于 180 秒才算活着。
9. `python checks\verify_deploy.py --base D:\bots\甲 -c agents\甲.json`：`status=PASS`、`serving=1`。
10. **恢复看门狗**，并确认那条任务的状态真的回到 Ready。

回滚后那个 `deploy/*` 标注 tag 留在原地不要删——它是「这台机器经过这一版」的证据。

## 备份的验收口径

这条是被证伪过的，值得单独写：

> 备份的验收口径是「**能不能在别处还原出一个工作树**」，不是「sha 对得上」。

增量 bundle（`git bundle create x.bundle <起点>..main`）把 `<起点>` 记成先决提交，要还原它得先拥有它本来要保护的那个仓库。它的 `list-heads` 看着完全正常，`git bundle verify` 在没有仓库的目录下只会说 `error: need a repository to verify a bundle`，也就是说你以为「验过了」其实没验。

做法：用**自包含的全量 bundle**（`git bundle create x.bundle main --tags`），并且真的 `git clone <bundle>` 到别处再 `git log` 对一次。clone 成功才算备份存在。注意 `main` 一个分支不够——要推的东西可能带着本地分支和一批 tag，`--all` 或点名补齐。

## 推上游之前

- `git log --oneline` 看一眼要推的提交里有没有 secrets 级字面量。CI 有 secret 扫描那一格，它会挡住整个流水线；本机先扫一遍比在 CI 上试错快。
- 推完之后**盯 CI 到绿**，绿了才算这一版可用。红了就修到绿，不要先把 CI 关掉或者绕过那一格。
- 时间窗要算：如果靠定时任务去看 CI，窗口是「重试次数 × 任务间隔」，量出来是多少就是多少，别凭感觉。
- 实例目录的对齐靠的是那次 `git fetch`。远程改名之后 `git push` 会打印 `This repository moved`，它只是提示，但每次都要看见一次，把 `origin` URL 换成新地址更干净。

## 多实例，以及故意错开版本

几个实例没必要永远同版本。**故意错开**是可以的，但要写清楚，不然下一个人会把它当成「忘了升」而顺手对齐——那一改就动了正在服务的进程。

要写清楚的三件事，落在部署记录里而不是代码注释里：

- 哪个实例停在哪个提交、哪个 `deploy/*` tag 上；
- 为什么这次不动它（观察期、别人正在用、还是它就是不在范围）；
- 谁负责在什么时候把它拉上来。

`deploy/<实例>-<日期>` 这类标注 tag 只在本地打，**不推上游**：仓库是公开的，标签名里带着实例名和机器目录。发布用的 `v*` 标签才是推到上游的。

本次发 v0.10.0 就是这么安排的：发版和上线是两件事。`v0.10.0` 打出去的这一刻，**没有哪台线上机器在它上面**——观察中的那台停在发布前的 `main`，靠当天的标注 tag 说明「这台跑的是哪一版」，升它要等一个允许重启的窗口；另外两台一台停在更前面的版本、一台这一轮完全不在范围（进程不动、目录不动，连 remote 都不改）。下一个人看到版本不齐时，那一句「谁负责在什么时候把它拉上来」就填在这里。

## 长任务的自动化：不要指望单个 watcher

Windows 计划任务会静默地不再跑，而且 `LastTaskResult=0` 只说明「被调度了」，不说明里面那条命令做成了事；电池策略下默认压根不派发。所以别写一个长跑的 watcher 然后离开。

可用的形状是**可续跑的状态机**：

- 每次运行只做一步，把进度写进一个小状态文件（哪个提交已推、已经查到哪一步）；
- 判断完了如果还不干净，就只写一句 `HOLD: <原因>`，下一次接着从状态文件走；
- 全部条件满足时写一个**完成标志文件**，然后删掉自己所在的那条任务；
- 需要人点一下的那一步（浏览器授权）单独留一个可以反复双击的入口，不要吊在后台任务上等。

这样任务死了也只是晚一点到，不会整个流程丢在半路。

## 不要做的事

- 不要为了让某一项变绿去**结束进程**。`FAIL` 只说明该看哪一项，停进程仍用那个目录自己的 `scripts\stop.ps1`。
- 不要为了补锁文件里的 `created=` 那一行去重启进程，也不要手改 `state\bot.lock`。
- 不要为了制造 `logs\events.jsonl` 里的一行去群里 @ 机器人。
- 不要把密钥写进配置，也不要提交 `agents\` 下真实那份配置。
- 不要在没看清 DRY 输出之前跑真实执行；写运维脚本时默认只打印要做什么，加一个显式开关才动手。
