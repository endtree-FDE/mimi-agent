# 部署后验证

升完一个机器人就跑一次。脚本是只读的：不发飞书消息，不启动长连接，不写心跳，不删锁，不结束任何进程。这一页讲每一项看什么；升级和回滚按哪个顺序跑、哪一步不过就停手，见 [runbook-升级与回滚.md](runbook-升级与回滚.md)。

```text
powershell -File scripts\verify_windows.ps1 -Config D:\bots\甲\agents\甲.json,D:\bots\乙\agents\乙.json,D:\bots\丙\agents\丙.json
```

三个配置一次传齐。这样能同时看到另外两个还在不在，而不是只看刚启动的那一个。

只在 Windows 上跑。它要读本机进程。它会调用每个机器人的 `--doctor`。诊断不写心跳；程序装载配置时仍会打开已有的日志和 `state.db`，但不会发消息，也不会改锁。

## 它看什么

每一行都是 `OK`、`WARN` 或 `FAIL`。没有 `FAIL` 时退出码是 0，只有警告也是 0。有 `FAIL` 时退出码是 1。

- 本机所有 `agentbot.py`：进程号和所在目录。`--doctor`、`--check`、`--dry-run`、`--lock-test` 会列出来，但不当成正在服务。同一目录有两个正在服务的进程是 `FAIL`。Windows 上如果进程表没读到，这一项是 `WARN`（列不出进程），不会写成 `OK serving=0`。真的枚举到了进程、其中没有本机器人，才是 `serving=0`。
- 每个飞书应用的 `event consume`。同一个 profile、同一种事件只能有一个。自动认群时，进群和出群是另外两种事件，不算重复。`event _bus` 是 lark-cli 自己的总线，不算接收进程。同一种事件有两个是 `FAIL`。脚本只报告，不结束它们。后台没开通卡片回调时，没有 `card.action.trigger` 不算少一个进程，也不算机器人断线。
- 每个目录的 `state\bot.lock`。有 `created=` 时，要和进程的创建时间一致；有 `base=` 时，要和这个目录一致。对不上是 `FAIL`，意思是编号可能已经被别的程序复用。不要为此去结束那个进程。
- 旧锁只有一行进程号、没有 `created=`：进程如果仍是本目录的 `agentbot.py`，这是 `WARN`，不是失败。本版本第一次真正启动后会写成三行。不要为了补这一行去结束进程，也不要手改锁文件。
- `--doctor`。这是只读诊断：看登录、应用权限、网络。它不发消息。事件订阅不根据 `event list` 判断，只报需要哪些事件。诊断自己的 `FAIL` 会算进这次验证。参数不被这一版 `lark-cli` 接受，是 `WARN`，不是 `FAIL`。只拿到用户 token（`tokenType` 为 `user`）时，权限核对也是 `WARN`，请到开放平台看应用权限。
- 这个目录的 `agentbot.py` 里还没有 `--doctor`（旧版）时，验证只报 `WARN` 然后跳过。不会把不认识的参数交给旧程序，否则旧程序会把它当成真正的启动。
- `logs\events.jsonl` 最近 50 行里的错误码。只打工具名和错误码，不打原文。有错误码是 `WARN`（缺权限时本来就会有），不是 `FAIL`。文件还不存在，多半是刚启动、还没答过题，这一项是 `WARN`。不要为了制造这一行去群里 @ 它。
- 日志轮转。`stdout.log`、`stderr.log`、`bot.log` 超过约 2MB 却没有 `.1` 备份，是 `WARN`（轮转可能没生效）。有备份，或者还没到 2MB，是 `OK`。`events.jsonl` 和 `watchdog.log` 还不存在时，这一行是 OK，文字是「不存在（空）」，不是警告。另外三种日志不存在仍是 `WARN`。

目录名 `bot` 和 `bot2` 会分开列，不会因为前缀相同就当成同一个。

## 机器可读结论

要给脚本或工单看，用这一条：

```text
python checks\verify_deploy.py --base C:\bots\甲 [-c agents\甲.json] [--no-doctor]
```

输出一个 JSON，退出码 0 是 `PASS`、1 是 `FAIL`、2 是目录或配置没给对。`agents` 里只有一个 json 时会自动选它，不用写 `-c`。

顶层除了下面这几段，还有 `status`（就是 `PASS` 或 `FAIL`）、`fails` 和 `warns`（两组中文说明，`fails` 决定结论，`warns` 只提醒不改结论）、`base`（核对的目录）和 `checked_at`（这次核对的时刻，Unix 秒，不是可读时间）。要给脚本判断，读 `status` 和 `fails`；退出码只能区分「跑成了没有」，2 是参数或目录没给对，和机器人健康无关。`warns` 的条数不是固定的：带 `--doctor` 时，诊断里的 `WARN` 也会并进来，所以同一个目录不带 `--doctor` 可能只有 1 条，带上就有 3 条。

- `git`：HEAD、分支、最后一行提交、还没提交的改动、这个 HEAD 上的 tag。读不到 git 只是提示，不算失败。HEAD 上没有任何 tag、或者工作区还有未提交改动时，会写进 `warns` 提醒「说不清这台跑的是哪版」，但不改结论——线上目录常留着本地想保的文件，那不该让核对失败。
- `heartbeat`：年龄和告警线。线取配置里的 `alerts.unhealthy_after_sec`，没写就是 180 秒。超过线或文件不存在是 `FAIL`。
- `deploy_lock`：`state\deploy.lock` 在不在、年龄和 ttl、看门狗此刻有没有让路。让路或过期都只提示，不改结论，这个脚本也不删锁。
- `topology`：本目录正在服务的进程数（不是 1 就 `FAIL`）、同一 profile 的 `event consume` 和 `lark-cli event _bus` 条数、别的目录的 `agentbot.py` 条数。归属判定沿用 `verify_windows.ps1` 那一套，不另写规则。列不出进程时只提示，不猜。
- `runtime`：本目录那个服务进程的启动时间，和顶层 `.py` 最新的改动时间比一比。进程比代码旧就在 `warns` 里说一句「要重启才生效」，不改结论；读不到启动时间、或目录里没有顶层 `.py` 时不猜，直接留空。只改文档或 `checks` 下的脚本时它也会提醒，按情况忽略。这一条是给「代码合完了、进程还是旧的」那段窗口写的。
- `config`：这个文件的 sha256 和字节数、profile、`kb_dir` 和它解析出来是否在仓库外、群和白名单条数、`scheduled`（早晨摘要、播报、调用记录报告三项开没开）。`kb` 还在不在、能检索到几条资料（认 `.md`、`.txt`、`.markdown`，和提示词里那份目录同一个口径）。目录不存在或一条都没有时只提醒，不改结论；知识库检索和目录都关着时不提醒，那是正常配置。
- `doctor`：只有带 `--doctor` 时才有这一段，里面是 `exit_code` 和 `rows` 两项；诊断的每一行在 `rows` 这个数组里，每行拆成 `level`、`name`、`info`。取行要读 `doctor` 里的 `rows`，直接遍历 `doctor` 本身只会拿到 `exit_code`、`rows` 两个键名。它的 `FAIL` 会算进这次的结论，`WARN` 只提示并写进 `warns`。其中 `restart` 那一行是近 6 小时 consumer 退了几次、按原因分开数（`alerts.restart_window_sec`、`alerts.restart_warn_after` 可调）；退出会自愈重连，所以断线提醒看不出来，要看累计。`service` 说进程在跑、正在停还是已停（已停不算失败），`last_ok` 是最近一次成功应答的时间，`last_fail` 是最近一条失败的一句话（不打堆栈；之后已经成功过则仍是 OK），`checklist` 把通过、警告、失败的项名列在一起。这四行只读本机文件，不发消息。加 `--no-doctor` 就完全不跑诊断，适合没装 `lark-cli` 的机器。

## 不要做的事

不要在验证脚本后面再去停进程。`FAIL` 只说明要看哪一项。结束进程仍用那个目录自己的 `scripts\stop.ps1`。

## 回答质量

进程和权限看完之后，如果这次升级动过模型、提示词或工具，再跑 [回归测试.md](回归测试.md)。那一套不调用本页的脚本，不连接飞书，也不拿单实例锁。可以指向正在使用的配置文件，原文件不会被改。
