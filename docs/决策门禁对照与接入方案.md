# 决策门禁对照与接入方案（juchang-skills 三件套 → mimi）

2026-11-08 C1 调研定稿。调研对象：2026 年生产级 agent 决策门禁 / 人类在环（HITL）审批的主流模式；对照物：juchang-decision-gate 的三维路由（证据状态 × 动作等级 × 可逆性）。结论先行：**四大框架都把 HITL 做成「暂停-恢复」或「权限规则」，但没有任何一家把「证据状态」作为执行前的硬门；这正是 mimi 接入 juchang 决策门禁的价值位**——evidencegate_check（内容可信度，已上线）的输出作为 decision-gate（动作是否允许）的输入，两门各守一段。

## 一、四个成熟案例的模式

### 1. LangGraph interrupt（动态中断 + 状态快照恢复）

来源：LangChain 官方文档「Interrupts」（docs.langchain.com，2026 当前版）。

- 机制：节点里任意位置调 `interrupt(payload)`，图暂停、checkpointer 存完整状态快照，payload 透出给调用方；恢复用 `Command(resume=...)`，resume 值成为 `interrupt()` 的返回值。`thread_id` 是持久指针。
- 关键纪律（官方明文）：中断后**节点从头重跑**，所以 interrupt 之前的副作用必须幂等；不要 try/except 包住 interrupt；多个 interrupt 严格按索引匹配。
- 可选 `response_schema`（Pydantic/TypedDict）对 resume 值做类型校验。
- 静态断点 `interrupt_before` 官方自己注明不适合 HITL，只用于调试。

### 2. OpenAI Agents SDK approval（needs_approval + RunState）

来源：OpenAI Agents SDK 官方文档「Human-in-the-loop」（openai.github.io，2026 当前版）。

- 机制：工具声明 `needs_approval=True` 或传 per-call 可调用规则；运行暂停后 `RunResult.interruptions` 挂 `ToolApprovalItem`；`RunState` 可序列化，`state.approve()/reject()` 后恢复运行。
- 关键纪律（官方明文）：
  - **参数解析不了就 fail closed**：参数缺失/空/坏 JSON/非对象/含 NaN 时，不调规则、直接要求人工审批。
  - `always_approve` 粘性决定有作用域警告：shell/文件工具的粘性决定按「工具类型+名字」共享，可能跨 agent 越权。
  - 审批人身份必须服务端鉴权，**不能从请求体里取**；持有 run id 不等于授权。
  - 「批准只允许执行，不保证恰好一次」：外部副作用要幂等键；崩溃恢复先与目的地对账，读不到结果不能证明没执行过。
- 手册同时给出自动审批回调（on_approval）与人工中断两档。

### 3. Claude Code permission（模式阶梯 + allow/ask/deny 规则）

来源：Claude Code 官方权限体系，2026 年多篇中文梳理（腾讯开发者文章等）交叉一致。

- 机制：settings.json 里 `permissions.allow / ask / deny` 三张规则表，按工具+模式精确匹配（如 `Bash(npm run test:*)`）；六档模式 default / acceptEdits / plan / auto / dontAsk / bypassPermissions 覆盖从强管控到全自动的梯度。
- 2026-08 起 AutoMode 默认开启：独立分类器实时判断「是否可逆、是否越界」，只有真正危险的命令才打断（据称危险命令拦截率 13.6%→89%）。

### 4. CrewAI human_input（提示级询问）

CrewAI 的任务级 `human_input=True`：任务收尾前提示人类给意见，回复 consensus/terminate 决定是否继续。它是「提示词级流程建议」，不是硬门——juchang 术语里属于「流程建议」而非「门禁」。它的存在恰好反证了生产级做法的共识：**HITL 要落在暂停-恢复和权限规则上，不能落在模型自觉上**。

## 二、抄什么 / 不抄什么（对照 juchang-decision-gate 三维路由）

| # | 案例的做法 | 抄不抄 | 在 mimi 里怎么落 |
|---|---|---|---|
| 1 | LangGraph：interrupt 前副作用必须幂等（节点恢复会重跑） | **抄** | 写提案→确认→执行三段本来就把副作用放在确认之后；确认码一次性作废（used_confirm_tokens 表）已是幂等闸 |
| 2 | LangGraph：interrupt payload 带完整动作细节给审批人 | **抄** | 已有：提案卡片正文=将要执行什么+影响谁+谁可以操作；门禁路由结论也进这段文案 |
| 3 | LangGraph：response_schema 对恢复值做类型校验 | 抄思想 | 门禁输入 JSON 由 CLI 严格枚举校验（L0-L3 等），非法值 exit 2 拒收，不猜不补 |
| 4 | LangGraph：checkpointer 全图状态快照 | **不抄** | mimi 的 pending_writes SQLite 已够：待确认动作持久化、重启不丢；不需要图级快照基建 |
| 5 | LangGraph：暂停无限期等恢复 | **不抄** | mimi 确认码/卡片有 TTL（300s/600s）过期作废，群聊场景比「无限等」更安全 |
| 6 | OpenAI：参数解析失败 → fail closed 要求人工 | **抄（重点）** | 同构于 evidencegate MODEL_OUTPUT_INVALID：内容校验不过→写提案降级/阻断；决策门禁输入枚举非法→拒绝评估并如实报错 |
| 7 | OpenAI：审批人身份服务端鉴权，请求体身份不算数 | **抄** | 已有：`_same_write_actor` 只有发起人本人在原会话能确认；白名单 + 确认码 + 卡片 token 三重绑定 |
| 8 | OpenAI：批准≠恰好一次，外部动作要幂等键 | **抄** | 确认码/按钮 token 一次性；重复点旧卡片被 action_hash 对账拒绝 |
| 9 | OpenAI：always_approve 粘性批准 | **不抄** | mimi 每次写提案独立确认，不做「以后都允许」；粘性批准正是 OpenAI 自己警告的越权坑 |
| 10 | OpenAI：RunState 全量序列化跨进程运输 | **不抄** | mimi 审批不跨进程运输，本机 SQLite 足够，避免快照被替换的整类风险 |
| 11 | Claude Code：allow/ask/deny 三张规则表 | **抄（形状）** | mimi 配置声明「哪些写工具过门禁、各是什么等级」（`write.decision_gate.tools`），配置化而非写死，对应 allow(不过门)/ask(过门) 的分界 |
| 12 | Claude Code：模式阶梯（六档从强到全自动） | 抄对照 | juchang 的 L0-L3 本来就是阶梯；mimi 只读工具不过门（L0），写动作按配置分级进门 |
| 13 | Claude Code：AutoMode 分类器自动判可逆性 | **不抄** | 门禁必须确定性、可审计：分类器输出不可复现，进不了门禁路径。juchang 契约明言「不得为让动作通过而调参」，同理不让 LLM 参与判门 |
| 14 | Claude Code：bypassPermissions 逃生舱 | **不抄** | mimi 确认不能关掉（confirm_mode.py 红线），门禁同样不给绕过键；回滚靠 git/tag/runbook，不靠绕闸 |
| 15 | CrewAI：提示级 human_input | **不抄** | 证明「流程建议」不够硬；mimi 门禁是代码路径上的闸，不是提示词里的一句叮嘱 |
| 16 | 四家共同盲区：证据状态不进门 | —— | juchang 独有：conflict/missing 证据无条件阻断执行（哪怕数值再好）；partial 阻断 L2/L3。mimi 接入后获得这门：evidencegate 三路由 → evidenceState 输入 |
| 17 | juchang：queue priority 只排先后不给权限 | **抄** | 门禁摘要里明确「处理顺序不代表允许执行」，防止把优先级当授权 |
| 18 | juchang：预计损失指数/折算影响量是操作比较模型，非事实 | **抄** | 话术原样保留「不描述为钱、确定性、真相或许可」的非声称边界 |

一句话总结：**抄「fail closed、幂等、鉴权绑定、配置化分级」四条工程纪律；不抄「图快照、粘性批准、LLM 分类器、绕过键」四个复杂度/风险源；juchang 的证据硬门是四家都没有的增量，也是本次接入的核心价值。**

## 三、M2 适配设计（mimi 场景映射）

### 3.1 双门关系（先理清再动手）

```
群友消息/图片
   │
   ▼
[门一：evidencegate_check]（已上线，tools.evidencegate_check）
   管「内容可信度」：模型输出 JSON → 三路由 ACCEPT_CANDIDATE / HUMAN_REVIEW / MODEL_OUTPUT_INVALID
   │  路由结果落进 evidence 注册表（chat 级、带时间戳、带审计）
   ▼
[门二：decision_gate_check]（本次接入，tools.decision_gate_check + write.decision_gate）
   管「动作是否允许」：证据状态 × 动作等级 × 可逆性 → 路由
   ├─ executionMode=blocked        → 拒绝提案（依据冲突/缺失），审计 write_blocked
   ├─ executionMode=manual_only    → 拒绝代执行（L3/不可逆），提示人工自行操作
   ├─ executionMode=after_approval → 走既有确认流（named=白名单发起人确认后执行；dual=发起人确认只记下，另一位白名单管理员回复「复核 码」才执行）
   └─ executionMode=automatic      → 仍走既有确认流（mimi 红线：确认不能关，门禁只能加严不能放宽）
   │
   ▼
既有写提案流（propose_write → pending → 确认码/卡片 → confirm → 执行 → 审计）
```

关键原则：**decision-gate 是包裹增强，不是另起一层**——它插在 `propose_write` 入口处，输出三种结果：放行进确认流 / 拒绝并说明依据 / 拒绝代执行。它永远不能绕过或替代确认码；`automatic` 在 mimi 语境=「允许提案进入确认流」，不是「免确认执行」。

### 3.2 「具名人类决定」→ mimi write 确认流

| juchang 概念 | mimi 映射 |
|---|---|
| named approval（负责人批准） | 白名单发起人 + 确认码/卡片（既有 `_propose_record`/`confirm`，零改动） |
| dual approval（双人复核） | 已实现（此前 v1 降级为文案提示）：门禁返回 dual 时发起人确认只记下不执行，需另一位写入白名单管理员本会话回复「复核 码」才真正执行；边界（发起人自己复核不算、复核人不在白名单拒绝、取消不担）有测试写死。抄的是「执行前第二道闸」的思路，不抄的是 LangGraph 式进程内挂起——mimi 的复核落在群会话里，跨进程状态由确认码账本管 |
| human preparation（人工处理） | 提示群友自行操作，机器人不代做 |
| 审计留痕含路由依据 | `write_proposed`/`write_blocked` 审计事件带 gate 字段：actionLevel、evidenceState（含来源）、executionMode、approvalMode、reasons 摘要 |

### 3.3 证据状态从哪来（确定性优先）

- 写提案依赖 OCR/文档内容时：SKILL.md 指示模型先跑 `evidencegate_check`；`propose_write` 前由门禁包裹层查 **evidence 注册表**（同 chat 最近一次 evidencegate_check 结果与时间戳）→ ACCEPT_CANDIDATE=sufficient、HUMAN_REVIEW=partial、MODEL_OUTPUT_INVALID=missing。
- 注册表没有近期记录：用配置默认 `evidence_default`（默认 sufficient=「无证据声明的普通写入，发起人请求即依据」）；注册表有记录但超时（`evidence_window_sec`，默认 900s）同样回默认并在审计里写明来源是默认。
- 来源永远写进审计（`evidence_source: "evidencegate:ACCEPT_CANDIDATE@ts"` 或 `"default"`），可复核、不猜。

### 3.4 动作等级与可逆性（配置化，不写死）

`write.decision_gate.tools` 声明每个写工具的等级（对应 2026-11-08 与主人讨论的结论：按「动作」分级而非按「文件」）：

```json
"write": {
  "decision_gate": {
    "enabled": true,
    "tools": {
      "docs_create": "L2",
      "docs_append": "L2",
      "calendar_create": "L2",
      "base_create": "L2",
      "memory_propose": "L2",
      "calendar_delete": "L3"
    },
    "evidence_window_sec": 900,
    "evidence_default": "sufficient"
  }
}
```

未列出的写工具不过门禁（现状不变）；只读工具一律不过门禁。其余维度（reversibility/complexity/likelihood/impact）由代码内固定映射表从等级推导（L2=reversible+simple 等，契约注释写明），可在 `tools` 条目里用对象形式覆盖（`{"level":"L2","reversibility":"compensatable"}`）。

### 3.7 route-gate 源码的移植纪律

juchang-skills 仓里 `run-decision-gate.mjs` 的核心逻辑 import 自仓库外（zhuantang-art 主仓 `app/src/lib/admin/route-gate.ts` + `decision-math.ts`），技能包不自包含。处理：两份 TS 源是纯类型注解 TS，**机械剥类型移植成 .mjs**（不重写公式、不调参数），mimi 技能包内自包含；用**上游 16 条测试原样移植**（只改 import 路径）跑 `node --test` 验证行为等价。TS 原文件不入库（避免 Node 23.6- 才能跑的 type stripping 依赖；CI runner Node 版本不可控）。

## 四、验收与回滚

- 验收：群友发起写提案时，门禁按证据状态+动作等级给出明确路由（允许进确认流 / 需确认 / 阻断 / 只允许人工）；审计 `write_blocked`/`write_proposed` 含路由依据（gate 字段）；三个只读工具默认关、开启后路径与参数安全；上游 route-gate 测试全绿证明公式等价；全量测试 476+N 双编码全绿。
- 回滚：三个工具与包裹层全部默认关，回滚=配置去掉 `tools.decision_gate_check.enabled` / `tools.evidence_replay_check.enabled` / `tools.receipt_verify.enabled` 与 `write.decision_gate`（或整段删掉）；代码回滚走 `git revert` 单提交；实例回滚照 runbook 四步退上一个部署 tag。
- 零写入红线不动：三个 skill 脚本只读，不写文件、不发消息、不改配置；门禁只拦截或放行，不代替执行。
