# 双人复核离线演练

这一页只说明怎么演决策门禁的双人复核（`approval: dual`）。不改仓库默认配置，也不把日常的 L2 抬成 dual。

机制在 `tools.py` 的 `review`：发起人先确认，只记下；另一位写入白名单管理员在同一会话回复「复核」加同一串数字，才执行。只有一位确认时，飞书上的数据不动。生产上的幕幕和 Mimi 继续用 L2，不启用 dual。

键的说明见 [agents/CONFIG.md](../agents/CONFIG.md) 的 `write.decision_gate`。路由怎么来的见 [决策门禁对照与接入方案.md](决策门禁对照与接入方案.md)。

## 何时用

双人复核留给高风险写。`skills/juchang-decision-gate/scripts/route-gate.mjs` 的 `approvalMode` 在这些情况下给出 `dual`：

- 动作等级是 L3。执行路由同时是 `manual_only`：机器人拒绝代做，没有确认流，演不到「复核」。
- 动作等级是 L2，并且影响是 `critical`，或预计损失分档是 critical，或影响传播分档是 extensive。执行路由是 `after_approval`，这才进入两步确认。

日常把写工具写成字符串 `"L2"` 时，影响按 medium 推导，审批是 `named`（负责人批准）。发起人一个人确认就会执行，回复里没有「复核」。

配置里能覆盖的维度只有可逆性、复杂度、可能性、影响。沙箱要走到「dual 且仍进确认流」，把某一个写工具的 `impact` 临时写成 `critical`，等级仍写 L2。传播范围那条由离线测试覆盖，配置里没有对应的键。

## 离线先跑哪些测试

在仓库根目录跑。这两条不连飞书，也不改配置。

```text
node --test skills/juchang-decision-gate/scripts/route-gate.test.mjs
python tests/test_juchang.py
```

`node --test` 看这几条用例名：

- `a public write always requires named approval`：L2 加 medium，日常路径，审批是 named。
- `critical public changes use two-person approval even below L3`：L2 加 impact critical，审批是 dual，执行是 after_approval。
- `irreversible or destructive actions stay manual and require two-person approval`：L3，审批是 dual，执行是 manual_only。
- `wide downstream influence selects collaboration and stronger approval`：传播到 extensive 时审批是 dual。

`python tests/test_juchang.py` 看这几条打印出来的名字：

- `test_gate_wrapper` 里的「dual 审批提示两步确认与另一位管理员」「dual 路由进审计 approval=dual」。触发配置就是 `{"level": "L2", "impact": "critical"}`。
- `test_dual_review`：第一位确认不执行；发起人自己复核不算；第二位白名单管理员复核后才执行；取消不挡；白名单外的人被拒绝并留下 `write_denied`；非 dual 的提案不走复核；「复核」加数字能进确认命令。
- `test_statics` 里的「示例里写提案门禁默认关，试运行只声明 docs_create 与 base_create 为 L2」：`agents/example.json` 的 `write.decision_gate.enabled` 是 false，`tools` 只有 `docs_create` 与 `base_create`，都是 `"L2"`。

`tests/run_tests.py` 里还有一条集成：复核命令不调模型。发起人自己复核被拒，第二位白名单管理员复核后回复「已完成」，重放和错码都失效。演练前跑上面两条即可。改过命令路径时再跑整套 `python tests/run_tests.py`。

## 沙箱里真人走一遍

只用沙箱实例。`agents/example.json` 保持不动。幕幕和 Mimi 正在跑的那份配置保持不动。改过的沙箱 json 不要提交。

沙箱用自己的文件夹编号。演练文档建在沙箱文件夹里，演完删掉。

1. 把沙箱配置复制一份留底。
2. `write.allowed_users` 里至少有两位管理员。下面称发起人为小李，另一位是复核人。两位都在白名单里。
3. 沙箱副本里 `write.decision_gate.enabled` 为 true。只改要演的那一个写工具，等级保持 L2，影响临时写成 critical：

```json
"docs_create": {"level": "L2", "impact": "critical"}
```

其余写工具仍是 `"L2"`。

4. 只重启沙箱。已经在跑就平滑重启，还没启动就启动，配置都指向沙箱那一份：

```text
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\reload.ps1 -Config agents\<沙箱配置>.json
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\start.ps1 -Config agents\<沙箱配置>.json
```

5. 小李在沙箱群 @ 机器人，让它新建一份标题为「演练」的文档。
6. 回复里要有「双人复核」。确认码模式下还会写出「确认」和「复核」加同一串数字，并写明只有一位确认不会动任何数据。没有「双人复核」就让小李取消，先核对第 3 步。
7. 小李先确认。点按钮时点卡片上的「确认」；确认码模式则 @ 机器人回复「确认」加数字。机器人回答「第一位确认已记下」。按钮模式的卡片标题变成「还差复核」，正文里有「复核」加数字。这时沙箱文件夹里还没有这份新文档。
8. 复核人在同一个会话 @ 机器人，回复「复核」加同一串数字。应看到「已完成」。小李自己发「复核」会被拒绝。白名单外的人发「复核」也会被拒绝，审计里留 `write_denied`。
9. 实例目录的 `audit/*.jsonl` 里，这次应有 `write_proposed`（`gate.approval` 为 `dual`，`gate.level` 为 `L2`，`gate.execution` 为 `after_approval`），然后两条 `write_confirmed`（`detail` 分别为 `dual first`、`dual second`），再是 `write_done`。审计不写确认码，也不写人的编号。
10. 两步共用原来的有效期：按钮默认约 10 分钟，确认码默认约 5 分钟。第一位记下之后不重新计时。超时后码作废，数据不动。

取消走发起人。第二位复核之前，小李回复「取消」加数字，或点卡片上的「取消」。应看到「已取消」，审计里没有这次的 `write_done`。

按钮模式的第一张卡片末尾写着「直接跟帖复核」。执行发生在下一步：小李点「确认」之后，卡片变成「还差复核」，复核人回复「复核」加数字。

## 立刻收回

同一次演练里做完，不要留到下一次启动。

1. 把那个写工具改回 `"docs_create": "L2"`。
2. 用同一条 reload 只重启沙箱。
3. 再让小李新建一份普通文档。回复里不再出现「双人复核」。小李一个人确认后就执行。审计里 `gate.approval` 为 `named`。
4. 删掉沙箱文件夹里的演练文档。

## 生产保持 L2

幕幕和 Mimi 的日常写动作保持 L2，不启用 dual。不要把这两份生产配置里的 `impact` 写成 `critical`，也不要把日常写工具改成 L3。模板 `agents/example.json` 里 `write.decision_gate.enabled` 维持 false，`tools` 只有 `docs_create` 与 `base_create`，都是 `"L2"`。本页不改这些默认。试运行只声明字符串 L2 时，dual 不会出现，一个人确认的行为和从前一样。
