# 升级、回滚和停机意图

这一页把两家飞书机器人的运维姿势落到本仓库已经有的脚本上。不新加命令，不改 `scripts\start.ps1`、`scripts\stop.ps1`、`scripts\reload.ps1`、`scripts\watchdog.ps1` 的默认行为，也不让看门狗多认一种「请保持停止」的文件。

对照的是：

- [dsh-lark-bot](https://github.com/PlutoKeating/dsh-lark-bot) 的 `upgrade --profile` 一次只动一个 profile；`--rollback` 按上次升级记下的版本退回，不另起一份旧进程；`service stop` 把停止意图写进 `service/.intent.json`，守护进程看到 stopped 就不把这个 profile 拉回来。计划任务里写的是这个 profile，不是一份示例配置。
- [Twinny](https://github.com/hachiwii/twinny) 换版本由一个独立 helper 做完：先停掉当前 daemon，再备份数据、换上新的 runner、启动。两分钟内新版本没有写上运行状态，helper 把数据和旧 runner 换回去，再启动旧版本。停和换是同一次动作。

本仓库没有那条升级命令，也没有一份会挡住看门狗的持久停止意图。对应的入口是实例目录里的 `scripts\stop.ps1`、`scripts\start.ps1`、`scripts\reload.ps1`、`scripts\register-tasks.ps1`，升级窗口仍用 `state\deploy.lock`。顺序和闸门以 [runbook-升级与回滚.md](runbook-升级与回滚.md) 为准，多个目录怎么逐个换以 [升级三个机器人.md](升级三个机器人.md) 为准，锁文件的三行以 [升级停机与单实例.md](升级停机与单实例.md) 为准。下面只补四条容易拆开做错的姿势。

示例一律用「甲」「乙」和 `agents\甲.json`。不要把密钥、群号或 open_id 写进任务参数或这份说明。

## 升级：停和换版本是同一步，一次只动一个

一次只升一个机器人的目录。乙还在跑的时候，不要停乙，也不要改乙的树。甲核对通过之前，不要开始乙。

「同一步」指的是：对这一个目录，从「进程还在跑旧代码」到「进程起来时已经是测过的那一版」，中间不插入另一个机器人，也不把停和换版本拆成两次来做。旁边的临时克隆里先跑完 `python tests\run_tests.py`，测试没过就不要停正在服务的那一个。这一条不变。

两种已经在用的切法都算同一步，只要中间不断开：

1. 目录跟得上上游时，按 [runbook-升级与回滚.md](runbook-升级与回滚.md)：先 `git merge --ff-only`（进程里仍是已经载入的旧代码），放上 `state\deploy.lock`，马上 `scripts\reload.ps1 -Config agents\甲.json`。合并和这次重启是同一次操作。
2. 要切到旁边测过的某个提交时，按 [升级三个机器人.md](升级三个机器人.md)：回到服务目录后放锁，接着 `scripts\stop.ps1`，接着把代码换到那个提交，接着 `scripts\start.ps1 -Config agents\甲.json`。停和换代码接着做。

先停下来、过几分钟再换，看门狗会把旧代码拉起来。它大约每 5 分钟看一次；心跳超过约 3 分钟，或者进程不在，它就在**这个目录**里执行 `stop.ps1` 再 `start.ps1`。换到一半被拉起来，跑的就是半套代码。

认不出 `state\deploy.lock` 的旧看门狗更要守住 runbook 的顺序：先把新的 `watchdog.ps1` 合并进这个目录，再放锁，然后立刻 reload。锁放在旧看门狗上不起作用。放锁用这个目录自己的 `scripts\botproc.ps1` 里的 `Set-DeployLock`，不要手改锁文件。核对通过再用 `Clear-DeployLock`。忘了释放，看门狗会一直让路，下一次真故障就没人拉。

`git reset --keep` 或切换到测过的提交时，留下 `agents\` 里已经填好的配置、`state`、`kb`、`memory`、`redact.txt` 和 `logs`。升级不要用 `git reset --hard`，也不要 `git clean`。

## 回滚：只退有问题的那一个，用 start.ps1 拉起来

只回滚刚升过、核对没过或行为不对的那一个目录。乙没动过就保持运行，用来对照。三个都要退时，仍是一个一个停、换、启。

换回去用哪条 git 命令，按 runbook 的回滚顺序和 [升级三个机器人.md](升级三个机器人.md) 的「回退这一个」。这一页不另给一条。无论哪条，顺序都是：

1. 在**当前这份代码**里运行 `scripts\stop.ps1`，确认这个目录的 `agentbot.py` 已经不在，`bot.pid`、`state\bot.lock`、`state\shutdown.request` 都已清掉。乙的进程还在。
2. 只把这一个目录的程序换回升级前记下的提交。不要覆盖 `agents\` 里的配置、`redact.txt`、`kb`、`memory`、`state`。
3. 用**换回去之后、这个目录里的** `scripts\start.ps1 -Config agents\甲.json` 启动。

三行锁还在时，不要直接运行旧版的 `python agentbot.py`。新锁是三行：进程号、`created=`、`base=`。旧程序把整份文件当成一个进程号，读不出数字就当成过期锁删掉，再启动一个。同一个飞书应用就会有两个接收进程。`stop.ps1` 会先删掉锁，再换回旧程序、再走那个目录的 `start.ps1`，才避开这件事。旧的 `start.ps1` 只读锁的第一行；新进程如果还没停，它会说 `already running`，不会开第二个。不要为了「看锁碍不碍事」去手动起旧进程。

退回到认不出 `deploy.lock` 的看门狗时，先停用**这一个**目录的看门狗计划任务，再动代码。启动失败就让那条任务留在停用，不要让它反复拉起坏实例。细节在 runbook 的回滚一节。

## 启动必须写 -Config，计划任务写死真实 json

`scripts\start.ps1`、`scripts\watchdog.ps1`、`scripts\reload.ps1`、`scripts\register-tasks.ps1` 的 `-Config` 默认都是 `agents\example.json`。那份文件是占位符，不是这台机器上正在服务的机器人。省略 `-Config` 时，脚本会去读示例配置：`reload.ps1` 会先停掉本目录进程，再按示例配置启动。

每次手工启动都写成：

```text
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\start.ps1 -Config agents\甲.json
```

平滑重启同样带上这份配置。`reload.ps1` 会把 `-Config` 交给 `start.ps1`：

```text
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\reload.ps1 -Config agents\甲.json
```

`scripts\register-tasks.ps1` 在注册那一刻把 `-Config` 写进计划任务的参数字符串。之后改文件名、或当时忘了传、用了默认的 `agents\example.json`，任务仍会一直启动注册时写死的那一份，直到用同一个 `-Name` 再注册一次。一台机器上每个机器人用不同的 `-Name`：同名任务会盖掉上一条。

注册：

```text
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\register-tasks.ps1 -Mode logon -Config agents\甲.json -Name 甲
```

注册完看这两条任务的参数，确认里面是 `agents\甲.json`，并且没有 `agents\example.json`：

```text
(Get-ScheduledTask -TaskName "甲-Start").Actions.Arguments
(Get-ScheduledTask -TaskName "甲-Watchdog").Actions.Arguments
```

两条都要带 `-File` 指向**这个目录**的 `scripts\start.ps1` 或 `scripts\watchdog.ps1`。看门狗重启时用的就是任务里这份 `-Config`。配置路径用仓库里的相对路径，不要带空格，也不要把密钥写进任务参数。

## 停机意图：现在就是 shutdown.request

本仓库的停止请求是 `state\shutdown.request`。触发方式就是这个目录的 `scripts\stop.ps1`，不另写文件，也不改看门狗。`reload.ps1` 和看门狗在进程还活着时重启，都是先调用这份 `stop.ps1`，所以走的是同一条请求。

`stop.ps1` 先读本目录的 `bot.pid`。编号对应的进程命令行确认是本目录的 `agentbot.py` 之后，才在 `state\shutdown.request` 里写下一行 Unix 时间。心跳循环大约每秒看一次这个文件；文件在，进程就置上停机标记，停掉自己拉起的长连接，主线程走到 `finish_shutdown`。正在答的题最多再等 `shutdown_wait_sec`（不写是 15 秒）。等完仍没写完，进程退出，这题在 `state.db` 里保持 `received`，不会被标成已回答。`stop.ps1` 大约每秒再核对一次，最多等 20 秒。进程自己退出就不再强行结束。到点仍是本机器人，才用原来的 `Stop-OwnedTree`（结束前再对命令行和创建时间）。编号已经是别的程序、或等待期间被换走，都不结束。无论是否结束进程，脚本都会清掉本目录的 `bot.pid`、`state\bot.lock` 和 `state\shutdown.request`。

`shutdown_wait_sec` 比 20 秒更长时，`stop.ps1` 仍会在大约 20 秒时结束还在跑的本目录进程。想少等，把配置写成 `0`，见 [agents/CONFIG.md](../agents/CONFIG.md)。这不改变停止脚本的等待。

`scripts\start.ps1` 发现本目录已经在跑就直接退出，这时不删 `shutdown.request`，避免把正在退出的进程当成没人要求停止。只有真正要启动新进程时才删这个文件。新进程起来后也会再清一次，避免上次留下的请求让这次刚启动就退出。

这和 dsh-lark-bot 的 `service/.intent.json` 不是同一件事。那边的文件会留着，守护进程看到 stopped 就不回拉。这边的 `shutdown.request` 在 `stop.ps1` 结束时被删掉。看门狗不读 `shutdown.request`。没有 `state\deploy.lock`、看门狗任务也还开着时，下一轮看门狗仍会把这个目录拉起来。升级窗口里挡住自动拉起，用已经有的 `Set-DeployLock`。回滚时要它停住，按 runbook 停用这一个目录的看门狗任务。不要为了模仿那份 intent 文件再添一种停机标记。

### 怎么验收

在这个机器人的目录里执行：

```text
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\stop.ps1
```

看这几件事，都不要靠往群里发消息：

| 看哪里 | 通过时是什么样 |
|---|---|
| 脚本打印 | `stopped` 后面是原来的进程号。已经不在会打印 `not running`。编号不是本机器人会打印 `left it alone`，那个进程还在。 |
| `bot.pid`、`state\bot.lock`、`state\shutdown.request` | 三条都已不在。请求文件只在等待的那大约 20 秒里存在，脚本返回之后应当已经删掉。 |
| `logs\bot.log` | 有一行 `shutdown done busy=`。`busy=True` 表示退出时还有题没写完；`busy=False` 表示没有还在答的题。强行结束得太快时这一行可能来不及落下，这时以脚本打印的 `stopped` 和进程已经不在为准。 |
| `state.db` 里还没答完的那条 | 状态仍是 `received`。 |
| `state\inflight.json` | 只有消息编号、阶段和开始时间，没有问题原文。 |
| 下次 `start.ps1 -Config agents\甲.json` | 没答完的那条补答一次，回复开头是「（延迟回复）」。同一条再失败一次就放弃。 |
| 别的目录 | 乙的 `agentbot.py` 还在，乙的锁文件还在。 |

升完或退完再跑 `python checks\verify_deploy.py --base <这个目录> -c agents\甲.json`。`status` 要是 `PASS`，`topology.serving` 要是 1。`warns` 的条数不当闸门。
